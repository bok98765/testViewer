# C++ 이미지 뷰어 개발 제안서 (Windows, Visual Studio 2022)

- 작성일: 2026-10-11
- 작성자: mason
- 상태: 초안 (2차: Qt 제외, Windows 전용으로 변경)

## 1. 요약

대용량 이미지와 사진 폴더를 빠르게 넘겨 볼 수 있는 Windows용 이미지 뷰어를 C++로 개발합니다.
Qt 같은 외부 UI 프레임워크 없이 Windows가 기본 제공하는 API(Win32, Direct2D, WIC)만으로 만들고, 컴파일러는 Visual Studio 2022(MSVC)를 씁니다.

Windows 전용 API를 쓰면 실행 파일이 작고(수 MB 수준 목표) 설치 없이 실행할 수 있으며, 외부 프레임워크의 라이선스 제약이 없습니다.

개발자 1명 기준 약 13주에 1.0을 내는 계획이며, 6주차에 핵심 기능만 갖춘 MVP를 먼저 내놓습니다.

> 이 문서의 일정과 성능 수치는 구현 전의 계획값과 목표값입니다. 3주차 프로토타입 측정 결과에 따라 조정합니다.

## 2. 배경과 목표

### 2.1 왜 만드는가

기존 뷰어들은 다음 중 하나 이상에서 아쉬움이 있습니다.

- 수천 장이 든 폴더를 열 때 썸네일 생성으로 한참 멈춥니다.
- 수천만 화소 이상의 큰 이미지에서 확대·이동이 끊깁니다.
- 실행이 무겁고, 더블클릭한 뒤 이미지가 뜰 때까지 시간이 걸립니다.
- 색 관리가 되지 않아 넓은 색 영역 모니터에서 색이 과장돼 보입니다.

### 2.2 목표

1. **빠른 응답**: 열기, 넘기기, 확대가 체감상 즉시 반응합니다.
2. **가벼움**: 실행 파일 하나로 동작하고, 설치와 추가 런타임이 필요 없습니다.
3. **넓은 형식 지원**: Windows에 설치된 코덱을 그대로 활용해 일반 형식부터 최신 형식과 RAW까지 엽니다.
4. **정확한 색**: ICC 프로필을 읽어 모니터에 맞게 보여 줍니다.
5. **Windows다운 동작**: 고해상도 배율, 어두운 테마, 탐색기 연동(파일 연결, 끌어다 놓기)을 제대로 지원합니다.

### 2.3 하지 않는 것

범위를 지키기 위해 1.0에서는 다음을 다루지 않습니다.

- 레이어, 브러시, 필터 같은 이미지 편집 (회전·자르기 등 기본 조작만 지원)
- 사진 라이브러리 관리 (태그 데이터베이스, 얼굴 인식, 클라우드 동기화)
- 동영상 재생
- Linux, macOS, 모바일, 웹 버전

## 5. 기술 선택

### 5.1 개발 환경

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| IDE·컴파일러 | Visual Studio 2022 (MSVC v143) | 전제 조건. 디버거, 프로파일러, 정적 분석이 통합돼 있음 |
| 언어 표준 | C++20 (`/std:c++20`), 필요 시 `/std:c++latest` | `std::span`, `concepts`, `std::jthread`, `std::stop_token` 사용. `std::expected`는 C++23 기능이라 `/std:c++latest`가 필요 |
| 프로젝트 형식 | Visual Studio 솔루션(`.sln`, `.vcxproj`) | Windows 전용이므로 MSBuild를 그대로 사용. 명령줄 빌드는 `msbuild`로 CI에서 실행 |
| 의존성 관리 | vcpkg 매니페스트 모드 | Visual Studio 2022에 통합돼 있어 `vcpkg.json`만 두면 자동으로 받음 |
| 대상 플랫폼 | x64, Windows 10 22H2 이상과 Windows 11 | 지원이 끝난 버전은 제외. 최소 버전은 10장에서 확정 |
| Windows SDK | 최신 Windows 11 SDK | 새 API를 쓰되 실행 시점에 지원 여부를 확인 |
| 런타임 링크 | 정적 CRT(`/MT`) | Visual C++ 재배포 패키지 없이 실행 파일 하나로 배포 |
| COM 사용 | WIL(Windows Implementation Library)과 C++/WinRT | COM 포인터와 오류 처리를 안전하고 짧게 작성 |

### 5.2 UI 방식

| 후보 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| **Win32 + Direct2D** | 가장 가볍고 빠름, 외부 의존성 없음, 창과 렌더링을 완전히 제어 | 컨트롤과 레이아웃을 직접 구성해야 함 | **채택** |
| WinUI 3 (Windows App SDK) | 최신 Windows 디자인, 풍부한 컨트롤 | 런타임 배포 필요, 시작이 느리고 무거움, C++에서 XAML 도구 지원이 약함 | 가벼움이라는 목표와 맞지 않아 제외 |
| MFC | Visual Studio에 포함, 대화상자·문서 구조 제공 | 오래된 설계, 고해상도와 어두운 테마 지원이 번거로움 | 제외 |
| Dear ImGui + Direct3D 11 | GPU 렌더링과 UI를 빠르게 구성 | 한글 입력, 접근성, 네이티브 메뉴·대화상자가 약함 | 개발 도구에는 좋으나 일반 사용자용으로는 부족 |

이미지 뷰어는 화면 대부분이 이미지 영역이고 컨트롤이 적어서, Win32로 직접 만드는 부담이 크지 않습니다.
메뉴, 파일 열기 대화상자, 인쇄 대화상자는 Windows 공용 대화상자를 그대로 쓰고, 도구 모음과 패널 정도만 직접 그립니다.

### 5.3 그래픽과 텍스트

| 영역 | 선택 | 내용 |
| --- | --- | --- |
| 렌더링 | Direct2D (Direct3D 11 장치 위) | GPU 가속 2D 렌더링. 이미지 확대·이동, 타일 표시, 효과(색 변환) 처리 |
| 화면 출력 | DXGI 플립 모델 스왑 체인 | 지연이 적고 창 크기 조절이 부드러움 |

### 5.4 이미지 디코딩

기본은 WIC(Windows Imaging Component)입니다. Windows에 코덱이 설치돼 있으면 추가 코드 없이 그 형식을 열 수 있고, 보안 업데이트도 Windows Update로 받습니다.

| 형식 | 방식 | 비고 |
| --- | --- | --- |
| JPEG, PNG, GIF, BMP, TIFF, ICO, JPEG XR, DDS | WIC 내장 코덱 | Windows에 기본 포함 |
| WebP | WIC + WebP 이미지 확장 | 최근 Windows에는 대부분 기본 설치 |
| HEIF/HEIC | WIC + HEIF 이미지 확장 | HEVC 코덱이 따로 필요할 수 있음 (7.2절) |
| AVIF | WIC + AV1 비디오 확장 | Microsoft Store에서 설치 |
| JPEG XL | WIC + JPEG XL 이미지 확장 | 최신 Windows 11에서 제공. 없으면 libjxl로 보완 검토 |
| 카메라 RAW | WIC + RAW 이미지 확장 | 지원 기종에 한계가 있으면 LibRaw로 보완 검토 |

**보완 라이브러리 (선택)**: WIC만으로 부족한 부분에 한해 vcpkg로 추가합니다.

| 라이브러리 | 쓰는 경우 |
| --- | --- |
| libjpeg-turbo | JPEG 디코딩 속도가 목표에 못 미칠 때. 축소 디코딩과 무손실 회전에도 사용 |
| libwebp, libavif, libjxl | 코덱 확장이 없는 PC에서도 열리게 하려면 |
| LibRaw | WIC RAW 확장이 지원하지 않는 카메라 기종 |
| Little CMS 2 | Direct2D 색 관리로 부족한 프로필 변환이 있을 때 |

어떤 보완 라이브러리를 넣을지는 3주차 프로토타입에서 WIC의 속도와 형식 지원을 측정한 뒤 정합니다. 넣을수록 실행 파일이 커지고 보안 업데이트를 직접 챙겨야 합니다.

솔루션은 세 프로젝트로 나눕니다.

| 프로젝트 | 종류 | 내용 |
| --- | --- | --- |
| `Core` | 정적 라이브러리 | 디코딩, 캐시, 스케줄러, 메타데이터. 창에 의존하지 않음 |

코어를 창과 분리하면 UI 없이 테스트와 벤치마크를 돌릴 수 있습니다.

### 6.2 핵심 구성 요소

**디코더 레지스트리**: 파일의 앞부분 바이트(매직 넘버)로 형식을 판별해 맞는 디코더를 고릅니다. 확장자는 믿지 않습니다. WIC 디코더와 보완 라이브러리 디코더가 같은 인터페이스를 구현하므로, 나머지 코드는 어느 쪽인지 알 필요가 없습니다.

```cpp
struct ImageInfo {
    uint32_t width, height;
    PixelFormat format;
    uint32_t frameCount;
    std::optional<IccProfile> icc;
    Orientation orientation;
};

class IDecoder {
public:
    virtual ~IDecoder() = default;
    virtual std::expected<ImageInfo, DecodeError> ReadInfo() = 0;
    // scale: 1, 2, 4, 8 중 디코더가 지원하는 축소 비율
    virtual std::expected<Bitmap, DecodeError> Decode(uint32_t frame, uint32_t scale, std::stop_token) = 0;
    // 영역 디코딩을 지원하지 않는 형식은 전체를 디코딩한 뒤 잘라 냄
    virtual std::expected<Bitmap, DecodeError> DecodeRegion(RECT region, uint32_t scale, std::stop_token) = 0;
};
```

**작업 스케줄러**: 스레드 풀에 우선순위 큐를 둡니다. 우선순위는 "지금 보는 이미지 > 바로 앞뒤 이미지 > 화면에 보이는 썸네일 > 나머지" 순서입니다. 사용자가 빨리 넘기면 필요 없어진 작업은 `std::stop_token`으로 즉시 취소합니다.

**이미지 캐시**: 디코딩된 비트맵을 메모리 상한(기본값은 시스템 RAM의 일정 비율, 설정 가능) 안에서 LRU로 관리합니다. GPU에 올린 Direct2D 비트맵도 VRAM 상한을 따로 둡니다.

**2단계 표시**: 이미지를 열면 먼저 축소 디코딩이나 내장 미리보기(또는 셸 썸네일)로 저해상도 화면을 즉시 보여 주고, 전체 해상도 디코딩이 끝나면 바꿔 끼웁니다. 넘기는 속도를 디코딩 속도와 분리하는 핵심 장치입니다.

**타일 표시**: 큰 이미지는 타일(예: 512×512)로 나눠 화면에 보이는 것만 GPU에 올립니다. Direct2D 비트맵의 최대 크기 제한을 넘는 이미지도 이 방식으로 처리합니다.

**장치 손실 처리**: GPU 드라이버 업데이트나 절전 복귀로 Direct3D 장치가 사라질 수 있습니다. 장치와 GPU 자원을 다시 만드는 경로를 처음부터 넣어 둡니다.

### 6.3 스레드 모델

| 스레드 | 역할 |
| --- | --- |
| UI 스레드 | 메시지 루프, 입력 처리, 화면 그리기. 파일 입출력과 디코딩은 절대 하지 않음 |
| 디코딩 풀 | CPU 코어 수에 맞춘 작업 스레드. 디코딩, 색 변환, 썸네일 요청 |
| 입출력 스레드 | 폴더 목록 읽기, 파일 변경 감시 |

- 스레드 간 데이터는 불변 비트맵을 `std::shared_ptr`로 넘기고, 결과는 `PostMessage`로 UI 스레드에 알립니다.
- WIC 객체는 스레드별로 COM을 초기화해 사용하고(다중 스레드 아파트), UI 스레드의 COM 객체와 섞지 않습니다.
- Direct2D 장치 컨텍스트는 UI 스레드에서만 씁니다. 작업 스레드는 CPU 메모리의 비트맵까지만 만듭니다.

## 7. 품질과 위험

### 7.1 성능 목표

기준 장비는 6코어 CPU, NVMe SSD, 외장 GPU 1개인 일반 데스크톱으로 잡습니다.

| 항목 | 목표 |
| --- | --- |
| 프로그램 시작부터 첫 이미지 표시 | 200ms 이내 (2,400만 화소 JPEG) |
| 다음 이미지로 넘기기 (미리 읽은 경우) | 한 프레임(16ms) 이내 |
| 다음 이미지로 넘기기 (미리 읽지 않은 경우) | 저해상도 미리보기 100ms 이내 |
| 확대·이동 | 초당 60프레임 유지 |
| 1만 장 폴더 열기 | 1초 이내에 조작 가능, 썸네일은 화면에 보이는 것부터 채움 |
| 1억 화소 이미지 | 메모리 사용이 상한을 넘지 않고 확대·이동이 끊기지 않음 |
| 대기 상태 메모리 | 100MB 이내 (캐시 제외) |
| 실행 파일 크기 | 5MB 이내 (보완 라이브러리 제외 기준) |

수치는 목표값입니다. 3주차 프로토타입에서 실제로 측정해 달성 가능성을 확인하고, 벤치마크를 CI에 넣어 이후 퇴보를 감지합니다.

### 7.2 위험과 대응

| 위험 | 영향 | 대응 |
| --- | --- | --- |
| **코덱 확장이 없는 PC** | HEIF, AVIF, JPEG XL, RAW는 Windows 코덱 확장이 있어야 열림. 없으면 "열 수 없음"이 됨 | 형식을 판별해 "이 형식은 ○○ 확장이 필요합니다"와 Microsoft Store 링크를 안내. 수요가 크면 보완 라이브러리를 내장 |
| **HEVC 코덱 라이선스** | HEIC 사진은 HEVC 코덱이 필요한데, PC에 따라 유료이거나 설치돼 있지 않음 | 코덱을 직접 내장하지 않고 Windows 확장에 맡김. 안내 문구 제공 |
| **WIC 성능 한계** | JPEG 디코딩이 libjpeg-turbo보다 느리거나 축소 디코딩이 제한적일 수 있음 | 3주차에 측정. 목표에 못 미치면 JPEG만 libjpeg-turbo로 교체 (디코더 인터페이스가 같아 교체가 쉬움) |
| **악성 이미지 파일** | 조작된 파일로 프로그램이 죽거나 취약점이 악용될 수 있음 | WIC 코덱은 Windows Update로 패치됨. 직접 넣는 라이브러리는 퍼징과 AddressSanitizer 적용, 이미지 크기와 메모리 할당에 상한 |
| **Win32 UI 개발 부담** | 컨트롤, 레이아웃, 접근성을 직접 구현해야 해서 일정이 늘 수 있음 | 공용 대화상자와 공용 컨트롤을 최대한 사용, 직접 그리는 UI는 도구 모음과 패널로 한정 |
| **고해상도·다중 모니터** | 배율이 다른 모니터 사이를 오갈 때 흐려지거나 크기가 틀어짐 | 처음부터 모니터별 DPI 인식 v2로 개발, 배율 100%·150%·200% 조합으로 테스트 |
| **GPU 드라이버 문제** | 특정 드라이버에서 화면이 깨지거나 장치가 사라짐 | 장치 손실 복구 경로, WARP 자동 전환, 수동 전환 옵션 |
| **Windows 버전 차이** | 새 API가 구버전에 없음 | 최소 지원 버전을 정하고, 새 API는 실행 시점에 확인 후 사용. Windows 10과 11 모두에서 테스트 |
| **일정 지연** | 1인 개발이라 막히면 전체가 밀림 | MVP를 먼저 내고, 1.0 기능은 우선순위 순으로 구현해 뒤쪽 항목을 잘라 낼 수 있게 함 |

Qt를 쓰지 않으므로 이전 안에 있던 LGPL 준수 문제는 사라졌습니다. 보완 라이브러리(libjpeg-turbo, libwebp, libavif, libjxl, Little CMS)는 모두 허용적 라이선스(BSD, MIT 계열)이고, LibRaw는 LGPL 또는 CDDL 중 선택이라 넣을 경우 조건을 확인해야 합니다.

### 7.3 테스트 전략

| 종류 | 내용 | 도구 |

## 10. 착수 전에 정할 것

다음 항목은 설계에 영향을 주므로 시작 전에 결정이 필요합니다.

1. **최소 지원 Windows 버전**: Windows 10을 지원할지, Windows 11만 지원할지. 쓸 수 있는 API와 테스트 범위가 달라집니다.
2. **코덱 정책**: 최신 형식을 Windows 코덱 확장에만 맡길지(작고 단순), 라이브러리를 내장할지(어디서나 열리지만 크고 유지 부담). 3주차 측정 후 확정합니다.
3. **배포 방식**: 단일 실행 파일, 설치 프로그램, Microsoft Store(MSIX) 중 무엇으로 낼지. 파일 연결 등록 방식과 코드 서명 필요 여부가 달라집니다.
4. **공개 여부**: 오픈소스로 공개할지, 비공개 또는 상용으로 배포할지.
5. **주요 사용자**: 3장의 세 부류 중 누구를 우선할지. RAW와 색 관리의 비중이 달라집니다.
6. **투입 인력과 기간**: 13주 계획은 1명 전일 기준입니다. 실제 조건에 맞춰 일정을 다시 잡습니다.
